## 1. 推荐结论

已把“分组”从部门标签改成资源池：**每个 Codex 资源组只挂 1 个 OpenAI OAuth 账号，同一责任人的 Key 固定在同一资源组；DeepSeek 和其他模型账号作为共享模型通道挂入各组，但不作为 GPT/Codex 兜底。**

这样做的核心目的不是把 Key 数机械平均，而是同时做到：

1. 同一个 Key 的 GPT/Codex 请求固定由本组唯一 OAuth 账号承载，停止在多个账号之间随机扇出。
2. 同名责任人的多个 Key 必须作为一个整体分配，避免同一个人因多 Key 被分到多个账号。
3. 按账号真实套餐容量加权，美西的 `pro` 和 `prolite` 不按同一负载硬分。
4. 每组混合重度、中度和轻度使用者，使账号负载接近其容量占比。
5. 单账号异常时只影响本组 Key，故障域和责任边界清晰，便于限流、迁移和追责。

目标拓扑：

```text
API Key
  └─ 一个资源组
       ├─ 一个 OAuth 账号：只承载 GPT / Codex
       └─ 共享 API 账号：只承载其已映射的 DeepSeek / 其他模型
```

当前没有真正可用的 GPT/Codex API 兜底账号。美西账号 58、60 和东京账号 22 虽然数据库平台字段为 `openai`、类型为 `apikey`，但近 30 天实际承载的是 DeepSeek、StepFun、GLM、NVIDIA 等模型，不能当作 Codex OAuth 的备用容量。

上线后的实时流量曾出现模型兼容 404，并短暂为每组增加第二个 OAuth。进一步核验确认这是全局模型映射缺口，不是单个组少挂账号；增加第二个 OAuth 不能解决问题，反而破坏“一号一组”的隔离边界，因此已撤回。`gpt-5.6-sol` 不支持的问题按当前决策忽略，本次不修改账号模型映射。

## 3. 分配口径

### 3.1 负载指标

每个 Key 的规划负载采用：

```text
规划负载 = max（最近 7 天 OAuth Token，最近 30 天 OAuth Token × 7 ÷ 30）
```

只统计 OAuth 账号承载的 Token，DeepSeek 和其他共享 API 模型流量不参与 Codex 主账号平衡。

采用 `max` 是为了同时覆盖最近突然变重的 Key 和过去 30 天持续稳定的 Key。这个数值是分组权重，不是账单或用量报表。

### 3.2 容量权重

美西当前按数据库套餐标签暂用以下权重：

- `pro`：20 份容量。
- `prolite`：5 份容量。
- 容量比为 4:1。

因此美西不能把 72 个生产 Key 平均分成每组 7 至 8 个。容量加权后的结果是：

- 6 个 Pro 组：每组 10 人、10 个 Key。
- 4 个 Prolite 组：每组 3 人、3 个 Key。

东京 4 个 OAuth 都是 `pro`，因此按人数和负载近似四等分：27、26、26、26。

### 3.3 重轻混排

在每个节点内部，按规划负载排序：

- 重度：前 20%。
- 中度：中间 40%。
- 轻度：后 40%。

分配时先按账号容量确定人数配额，再交换责任人以最小化“实际负载占比与账号容量占比”的差值。结果中重度和轻度使用者会被放在同一组，不把所有重度使用者堆到一起。

### 3.4 不进入生产分配的 Key

最近 30 天没有成功用量的 active Key 不参与资源平衡。本次按用户要求统一移入 `codex-unused` 并保留 active；该组不关联账号，因此这些 Key 会被明确隔离。确认恢复使用后，再分到当时“规划负载÷容量权重”最低的资源组。

## 10. 验收标准

迁移完成后必须同时满足：

- 每个生产 Key 的 Codex/GPT 请求只能出现在本组唯一 OAuth `account_id` 中。
- 同一 Key 使用 DeepSeek/其他模型而命中共享 API 账号不算“一个人用多个 Codex 账号”。
- 美西各组“实际规划负载占比”与“容量目标占比”偏差不超过 15%。
- 东京四组 OAuth 规划负载偏差不超过 15%，Key 数保持在 27/26/26/26 附近。
- 除明确隔离的 `codex-unused` 外，没有 active Key 指向已停用、已删除或没有账号的组。
- 共享 API 账号不能接收 GPT/Codex；需要检查模型路由和实际 `usage_logs.account_id`。
- 最近 30 天无成功用量的 28 个 Key 均位于 `codex-unused`，且该组没有账号关联。
- 网关“无可用账号”503 连续 7 天低于 1%；若某一组超过 1%，把轻度 Key 迁移到容量归一化负载最低的组，不给原组增加第二个 OAuth，也不恢复全池共享。
- 回滚时只需恢复备份的 `api_keys.group_id/status` 和 `account_groups` 关系，不删除 Key。

## 11. 后续维护规则

- 每周重新计算一次规划负载，不按请求数或 Key 数单独做判断。
- 只有某组容量归一化负载连续两周偏离目标超过 20%，或该组 503 超过 1%，才迁移 Key，避免频繁换组。
- 新 Key 默认先进入最轻负载组；如果责任人已有 Key，必须进入同一组。
- 账号替换时对原组做一对一替换，不迁移整组 Key，也不让两个 OAuth 长期同时关联该组。
- 任何新增 OAuth 账号都创建新的独立资源组，再重新计算 Key 分配；不要把新账号挂到多个现有组。
- 部门统计从 `group_id` 脱钩，改用 Key 名称前缀或独立责任人台账。

## 12. 关键假设与备选方案

本方案最脆弱的假设是：数据库中的 `pro` 与 `prolite` 实际容量约为 4:1。如果真实订阅权益不是这个比例，美西 10/3 的人数配额就需要重算。若实际容量相同，应改为 72 个生产 Key 在 10 个 OAuth 组间按 8/8/7/7/7/7/7/7/7/7 分配。

每组增加第二个 OAuth 的方案曾短暂实施，但复核后确认模型 404 来自全局模型映射缺口，增加账号既不能修复未映射模型，又会让同一个 GPT Key 接触多个账号，因此已经撤回。最终坚持“一号一组”：需要扩容时增加账号和独立组，再迁移 Key；不采用环形复用或全池共享。
