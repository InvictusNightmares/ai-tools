# Sub2API 美西、东京账号池使用评估与整改方案

> 评估时间：2026-08-20 13:44，Asia/Shanghai  
> 数据窗口：最近 30 天为 2026-07-21 13:44 至 2026-08-20 13:44；趋势与故障重点看最近 7 天  
> 数据来源：美西、东京 Sub2API PostgreSQL 只读聚合，未读取或落盘 API Key、OAuth Token、代理密码  
> 隐私处理：人员只使用 Key ID 和部门做分析，文档不记录姓名、邮箱、原始 IP

## 1. 结论先行

当前整改优先级是账号池容量、Key 与账号的双向全共享、限额保护，出口代理排在后面。

最近 7 天，美西总错误率约 22.3%，东京约 38.6%。其中，美西有 18,028 次、东京有 22,257 次错误属于网关侧 503，且没有选中任何上游账号。这类错误分别占两节点全部错误的约 93.9% 和 92.6%，说明账号池在部分时段已无可调度容量。此时先降低账号并发会扩大故障，不应作为第一步。

容量和隔离分两条线推进：

- 容量最低线：美西增加 4 个 Pro 20x，东京增加 4 个 Pro 20x。两边均分两批增加，每批 2 个，观察 3 至 7 天后再继续。
- 隔离推荐线：美西保持增加 4 个，东京增加 8 个 Pro 20x。美西形成 6 个子池，东京形成 4 个负载池，每个池至少 2 个账号。
- 代理：暂不要求立刻一号一代理。先解决容量、分池、Key 限额和访问控制。代理只用于可信、固定、合规的出口隔离，不用于规避平台规则。
- 中转：可以做 5% 至 10% 灰度和灾备，但按当前用量全量迁移并不比自建账号池便宜。APIKEY.FUN 外接版仅已定价的 GPT 文本模型约为 47,977 元/月；若客户端直接满足“仅限 Codex”组资格，约为 39,981 元/月。两者均未包含当前全部模型流量。

推荐目标方案的账号固定成本约为 4,800 美元/月，按 1 美元兑 7 元折算约 33,600 元/月。该数值不含 OpenAI API Key、Anthropic API Key 的按量账单、服务器、代理和运维人工。

## 3. 需要整改的核心问题

### 3.1 一个人使用多个上游账号

这是调度拓扑造成的系统性现象，不应简单归因于个人主动切号。

- 美西最近 7 天有 68 个 Key 产生成功请求，其中 15 个 Key 使用了 10 个及以上当前账号；Key ID 56 使用了全部 12 个当前 OpenAI 账号。
- 东京最近 7 天有约 90 个 Key 产生成功请求，其中 40 个使用了 4 至 5 个当前账号，26 个使用了全部 5 个账号。
- 最近 30 天，部分 Key 的账号数高于当前账号数，是因为窗口内包含已替换或已删除的历史账号，账号变动也扩大了关联面。

整改后不要求每个人永远锁死在单个账号，单个 Key 的可达账号应从“全池”收敛到“固定小池”：

- 正常情况下，同一 Key 只在 1 个池内调度。
- 单池保留 2 至 3 个账号做额度切换和故障转移。
- 任何 Key 最近 7 天不应再扇出到 4 个以上账号，特殊管理员和压测 Key 例外。

### 3.2 一个上游账号被过多人共享

当前两个方向同时失控：一个人会打多个账号，一个账号也被大量人员使用。

- 美西每个主力 OAuth 账号最近 30 天服务了 63 至 71 个不同 Key。
- 东京每个 OAuth 账号最近 30 天服务了 90 至 102 个不同 Key。
- 美西单个 OAuth 账号请求量约为 2.05 万至 7.69 万，相差约 3.7 倍。
- 东京单个 OAuth 账号请求量约为 3.54 万至 9.51 万，相差约 2.7 倍。

全池随机调度没有形成隔离，账号负载也不均衡。

建议按最近 7 天 Token 做加权，而不是只按人数平均：

- 重度：最近 7 天 Token 位于前 20%，权重 1.0。
- 中度：中间 40%，权重 0.5。
- 轻度：后 40%，权重 0.25。
- 每个 Pro 20x 账号目标不超过 3 至 4 个重度等价值，并保留至少 20% 的额度余量。
- 典型组合可以是 1 个重度加 2 个中度，或 1 个重度加 4 个轻度。

人数可作为二级约束：

| 使用形态 | 建议人数/账号 | 适用条件 |
| --- | ---: | --- |
| 重度 Agent 编程 | 2 至 4 人 | 长上下文、高频工具调用、经常使用 Sol |
| 中等研发使用 | 4 至 6 人 | 日常编码，重度与轻度混排 |
| 轻度使用 | 6 至 10 人 | 低频问答、短任务、主要使用 Terra/Luna |
| 上限 | 10 人左右 | 超过后应再拆池，不以继续提高并发代替扩容 |

这是内部容量与故障域建议，不是 OpenAI 官方公布的多人共享额度。实际使用还应确认订阅条款和组织授权。

### 3.3 Key、用户和分组均缺少保护

两个节点当前都存在以下问题：

- 所有 Key 由 1 个管理员用户持有，无法按真实人员审计、冻结和结算。
- 0 个 Key 配置了 5 小时、1 天、7 天限额或总配额。
- 0 个部门组配置 RPM、日限额、周限额或月限额。
- 0 个 Key 配置 IP 白名单。
- 美西有 3 个、东京有 22 个活跃 Key 在最近 30 天没有成功用量，需确认后停用。
- 美西“研发Grok”组有 Key 但没有账号，是一个不可服务的空组。

建议：

1. 为每个真实使用者建立独立用户，或至少为 Key 增加明确的责任人、部门和用途标签。
2. 给 Key 配置 5 小时和 7 天额度，先以当前 P95 用量的 1.2 倍为上限，再根据两周数据调整。
3. 给组配置 RPM 和周预算。重度 Key 的突发流量不能把整个账号池吃空。
4. 对固定 CI、办公出口、前置网关配置 IP 白名单。移动办公场景使用可信网关，不要维护大范围放行名单。
5. 连续 30 天无成功用量的 Key 先通知责任人，确认后禁用，不直接删除。

## 4. 推荐分池方案

### 4.1 美西

目标：10 个现有 OAuth 增加到 14 个，2 个 OpenAI API Key 账号独立作为按量兜底，不参与日常订阅池轮询。

建议把“研发Codex”拆成 6 个子组：`研发Codex-A` 至 `研发Codex-F`。

- 每组分配 2 至 3 个 OAuth 账号，14 个账号建议按 3、3、2、2、2、2 分配。
- 最近 7 天约 68 个活跃人员，按 Token 从高到低排序，再用最小负载优先算法分入 6 组。
- 每组约 11 至 12 人，每个账号约 4 至 6 人。
- 重度人员与轻度人员混排，使各组最近 7 天 Token 差异控制在 20% 以内。
- API Key 兜底组只在订阅池无可用账号时启用，并设置每日美元上限和告警。

### 4.2 东京

容量最低线是从 4 个 OAuth 增加到 8 个。这个数量能明显缓解无可用账号错误，但按最近 30 天 108 个活跃人员估算，仍约为 13.5 人/账号，不满足隔离目标。

推荐从 4 个增加到 12 个 OAuth，形成 4 个账号池：

| 账号池 | 绑定部门组 | 建议 OAuth 数 | 30 天 Token/账号 |
| --- | --- | ---: | ---: |
| T1 | 测试 + 运维 | 4 | 约 26.95 亿 |
| T2 | 大数据 + 运营 | 3 | 约 24.71 亿 |
| T3 | 产品 + 架构 | 2 | 约 30.95 亿 |
| T4 | UI + 嵌入式 | 3 | 约 25.98 亿 |

这个组合利用了“高用量组和低用量组搭配”的思路，账号平均负载相差约 25%，远好于当前全交叉随机调度。测试组人数较多，后续如仍出现高扇出或 503，可把 T1 增加到 5 个账号。若要把全部池控制到约 10 人/账号，东京应达到约 14 个 OAuth，即增加 10 个。

东京的 1 个 OpenAI API Key 账号同样建议只做按量兜底，并配置日预算，不与 12 个 OAuth 混成同一无差别池。

## 5. 是否需要每个账号配置代理

结论：现在不建议为了“防关联”立刻采购廉价住宅代理，也不建议使用轮换代理。当前数据没有显示大规模上游 403 或认证封禁，最严重的错误是 Sub2API 自身没有可调度账号。

代理可以解决的是出口故障域和地域一致性，不能替代容量、权限和合规治理。

可选方案：

| 方案 | 出口数量 | 月成本 | 建议 |
| --- | ---: | ---: | --- |
| 保持节点固定出口 | 2 | 0 增量 | 先执行，优先修容量和分池 |
| 每个账号池一个固定出口 | 美西 6 + 东京 4，共 10 | `10 × P` | 推荐作为第二阶段，P 为单个固定出口月价 |
| 每个 OAuth 一个固定出口 | 推荐线共 26 | `26 × P` | 仅在合规、稳定、可信供应商可保证时采用 |

出口要求：

- 固定 IP、固定国家或地区、长期不轮换。
- 使用可信供应商和加密隧道，不允许 TLS 中间人解密。
- 代理凭证独立存储和轮换，不写入仓库或报表。
- 先对一个非关键池灰度 7 天，观察延迟、连接失败和账号状态。
- 不使用代理绕过平台限制、地区限制或账号风控。

最近 7 天有一个匿名化来源 IP 同时访问美西和东京，且分别贡献约 4.99 万和 1.50 万请求。同一调用方在跨节点使用，但该地址是 Sub2API 的客户端来源，不等于 OpenAI 看到的上游出口。除非确认客户端 IP 被转发到上游，否则不能据此认定上游账号已因该 IP 关联。

## 6. 需要增加多少账号

### 6.1 容量估算

以最近 7 天网关侧容量失败近似未满足需求，并再保留 20% 余量：

`目标容量系数 = (成功数 + 网关容量失败数) ÷ 成功数 × 1.2`

- 美西目标系数约 1.51。现有 4 个 Pro 5x 和 6 个 Pro 20x，按 Plus 等价值约 140 单位，目标约 212 单位，缺口约 72 单位，对应增加 4 个 Pro 20x。
- 东京目标系数约 1.89。现有 4 个 Pro 20x，约 80 单位，目标约 151 单位，缺口约 71 单位，同样对应增加 4 个 Pro 20x。

该公式是假设额度消耗与套餐倍率近似线性，只适合采购规划，不是 OpenAI 官方容量承诺。模型、上下文、推理强度、工具和缓存都会改变实际额度消耗。

### 6.2 分阶段采购建议

| 阶段 | 美西新增 | 东京新增 | 目的 |
| --- | ---: | ---: | --- |
| 第一批 | 2 个 Pro 20x | 2 个 Pro 20x | 先降低 503，验证模型资格和调度 |
| 容量最低线 | 再加 2，共加 4 | 再加 2，共加 4 | 达到当前需求加 20% 余量的估算线 |
| 隔离推荐线 | 保持共加 4 | 再加 4，共加 8 | 美西 6 池、东京 4 池均有冗余 |
| 东京人数理想线 | 不变 | 再加 2，共加 10 | 东京约 7.7 个活跃人员/账号 |

采购检查点：每批账号上线后至少观察 3 至 7 天；只有网关 503 仍高于 1%、账号池余量低于 20% 或单池人数和负载超标时，才进入下一批。

“仅限 Codex”组的页面说明限制为 Codex App 和 Codex CLI。Sub2API 服务器到中转的调用是否满足该组资格不能自行假设。服务器侧通用接入应按外接版 0.6 倍率预算，除非供应商书面确认。

### 7.3 自建与中转怎么选

| 维度 | 自建账号池 | APIKEY.FUN 中转 |
| --- | --- | --- |
| 直接成本 | 推荐线约 33,600 元/月，另加 API 账单和运维 | 已定价 GPT 文本约 39,981 至 47,977 元/月 |
| 运维复杂度 | 高，需要账号、额度、分池、出口和恢复 | 低，一个上游 Key 即可 |
| 数据链路 | 自有节点后到模型提供方 | 多一个第三方中转，需评估代码和数据合规 |
| 模型兼容 | 当前已经覆盖多供应商和自定义模型 | 需逐项验证模型、端点、图片、流式和工具调用 |
| 故障域 | 自己管理，可多节点和多供应商 | 增加供应商集中故障和价格变化风险 |
| 扩容速度 | 采购和养护账号较慢 | 充值后按量扩容较快 |

建议采用混合方案：

1. 自建池继续承担稳定主流量，并先完成容量与隔离整改。
2. APIKEY.FUN 作为 5% 至 10% 灰度和灾备，只迁移已验证的 GPT 文本模型。
3. 连续验证 7 至 14 天，比较成功率、网关 503、上游 429/5xx、首 Token 延迟、总延迟、模型输出一致性和实际账单。
4. 如果中转节省的运维人工和故障损失高于每月约 6,400 至 14,400 元的直接成本差，再考虑扩大比例。
5. 不在一次切换中迁移 DeepSeek、Claude、图片和自动审查等未验证流量。

## 8. 其他需要补充的整改项

### 8.1 不要先降账号并发

账号当前配置为 10 至 20 并发，但本次数据没有请求级在途并发证据。最近 7 天已经大量出现无可用账号，直接把并发降到 2 至 4 会先扩大 503。正确顺序是：

1. 增加容量和建立分池。
2. 给 Key 和组设置 RPM、5 小时和 7 天限额。
3. 采集每账号实际并发、排队深度和额度消耗。
4. 再把并发逐步下调到实测 P95 加 20% 余量，而不是使用统一固定值。

### 8.2 把 API Key 上游与订阅上游分开

OpenAI API Key 账号是按量成本，OAuth 订阅账号是固定成本和额度窗口。两者混在同一普通池会隐藏真实成本，并在订阅耗尽时产生不可控账单。

- OAuth 池用于日常流量。
- API Key 池只做兜底，设置日预算、周预算和成本告警。
- 账单按 `account_id + model` 监控，不能只看全站 `actual_cost`。

### 8.3 建立容量与故障看板

最少监控：

- 每节点、每账号池的成功数、总错误数、网关无可用账号 503。
- 每账号 5 小时和 7 天额度、下次重置时间、可调度状态。
- 每 Key 最近 7 天 Token、账号扇出数、RPM 和失败率。
- 每池当前账号数、可用账号数、实际并发和队列深度。
- API Key 兜底账号的实际美元成本。
- 中转灰度的实际人民币成本、首 Token 延迟和模型兼容性。

### 8.4 数据库查询和报表安全

本次最初的一条错误联表查询把账号、Key 和用量明细直接相乘，产生了大临时文件，并在美西短暂返回 `No space left on device`。查询结束后，美西磁盘仍有约 25 GB 可用，东京约 18 GB 可用，说明不是长期磁盘占满，但报表查询仍可能影响生产。

后续报表应：

- 先分别聚合账号、Key、组和用量，再按组 ID 连接。
- 优先使用现有日汇总表和复合索引。
- 为只读报表设置语句超时和临时文件上限。
- 避免在生产库直接执行多张大表的 `COUNT(DISTINCT)` 全交叉查询。
- 长期将报表迁到只读副本或离线数仓。

## 9. 执行顺序与验收标准

### 第一阶段：1 至 3 天

- 建立 Key 责任人清单，确认 30 天无成功用量的 Key。
- 给 Key、组和 API Key 兜底账号配置限额与告警方案。
- 美西和东京各新增第一批 2 个 Pro 20x。
- 创建一个小流量分池，验证 Key 固定在 2 至 3 个账号内。
- 建立网关无可用账号 503 看板。

### 第二阶段：3 至 14 天

- 两边完成容量最低线，各累计增加 4 个 Pro 20x。
- 美西拆成 6 个子池，按最近 7 天 Token 做重度与轻度混排。
- 东京先完成 4 个池的拓扑；如按隔离推荐线实施，再增加 4 个账号达到总计 12 个 OAuth。
- 把 OpenAI API Key 账号迁入独立兜底池。
- 开始 APIKEY.FUN 5% 至 10% 的 GPT 文本灰度。

### 验收标准

- 网关无可用账号 503 小于总请求的 1%，连续 7 天达标。
- 总错误率小于 3%，上游 5xx 小于 1%。
- 任一普通 Key 最近 7 天最多使用 3 个上游账号。
- 任一账号池额度余量不低于 20%，各池 Token 差异不超过 20%。
- 所有 Key 有责任人、用途、过期策略和限额。
- 30 天无成功用量的 Key 完成确认并禁用。
- API Key 兜底池有日预算和成本告警。
- 中转灰度完成 Responses、流式、工具调用、推理强度、缓存、图片和模型别名兼容性记录。

## 10. 最终建议

1. 先扩容，不先降并发。美西和东京容量最低线都是各加 4 个 Pro 20x。
2. 美西按 14 个 OAuth、6 个子池落地，最近 7 天约 68 人，平均约 5 人/账号。
3. 东京若只加 4 个仍约 13.5 人/账号，只解决容量，不解决隔离；推荐加 8 个达到 12 个 OAuth，按 4、3、2、3 分到四个负载池。
4. 每个 Key 固定在一个小池，池内 2 至 3 个账号。一个人不再打全池，一个账号也不再服务整个节点。
5. 代理不是当前首要问题。先保持节点固定出口，第二阶段再评估每池一个固定出口。
6. 自建推荐线直接成本约 33,600 元/月，低于外接中转约 47,977 元/月。中转更适合灰度、灾备和降低运维负担，不建议未经验证直接全量替换。
7. 立即补上 Key/组限额、IP 白名单、责任人、过期和兜底成本告警，这些措施比继续堆账号更能防止下一次全池耗尽。
