# 域名入口首次连接失败的排查

日期：2026-11-17。承接[域名证书迁移](certificate-migration.md)。真实部署值和原始诊断记录保存在受控私有目录，本文仅使用通用角色。

## 现象与结论

用户报告多个公网服务首次访问失败，刷新后可能恢复，Agent 调用 API 也会断开。旧 IP 访问未出现同样现象。复测表明，失败并不限于每次的第一条请求，也会连续发生。

故障期间，本机发出包含业务域名的 TLS 握手后，多次在收到证书前遇到连接重置。同一时段，直接用 IP 连接能收到证书。抓包中异常重置包的特征指向中间链路。故障当时缺少另一个等长域名的同步对照，具体触发条件和设备仍待确认。

前一轮将这一现象仅记录为原因不明的偶发网络波动，验收覆盖不足：经已有代理成功访问，不能证明本机直连入口稳定。本次补充了固定服务器地址、物理接口、同端口不同 SNI 及抓包对照。

## 可复核证据

| 检查 | 结果与含义 |
| --- | --- |
| 固定真实地址并绑定物理网卡 | 仍可复现 TLS 握手重置，排除本机 DNS 结果和 TUN 分流是这批失败的必要条件 |
| 同一公网主机、原 API 监听、域名 SNI | 连续六次被重置，尚未收到服务端证书 |
| 同一监听、不发送域名 SNI 的 IP 连接 | 六次均进入证书校验，仅因域名证书不包含 IP 而正常拒绝；未跳过校验，也未恢复旧 IP 证书 |
| 服务端 TCP 头抓取 | 正常客户端包 TTL 为 49；失败时出现 TTL 为 180、确认号异常的 RST，随后才收到正常客户端清理连接的 RST；该失败序列中服务器未主动发送 RST |
| 服务器本机、域名和完整证书校验 | 六次独立连接全部成功 |
| 隔离客户端、现有自有代理 | API 及两套面板各六次独立 HTTPS 请求，十八次均成功并通过证书校验 |
| 候选规则、域名及仅 IP 两种连接元数据 | 三个公网入口各两种方式，六次全部成功 |
| 三项 Tailscale 私网服务 | 各三次，共九次可信 HTTPS 检查符合预期，继续保持私网访问 |

11 月 18 日复测时，本机对 API、两套面板和订阅域名的 IPv4 解析均指向预期服务器。在原 API 监听上固定服务器地址和端口，每轮打乱顺序测试四种情况。两个在用域名各六次通过证书校验。等长的保留测试域名和无 SNI 的 IP 连接也各六次收到证书，随后按预期因名称不匹配而终止。

实际公网入口也各直连三次。两套面板均返回 HTTP 200，API 的模型列表在未提供密钥时均返回预期的 HTTP 401。九次 HTTPS 握手全部成功。这次复测表明故障具有间歇性。要判断它是否只影响特定域名，仍需要在重置再次出现时取得同条件的域名对照。

匿名 API 入口成功只能证明连接和入口可达；尚未用用户报告的具体 Agent 完成真实请求及流式结束验收，不能据此宣称其所有中断已修复。

## 11 月 18 日 API 再次无法访问

本次复现时，Mac 系统将 API 域名解析到了正确地址。绑定物理网卡请求管理页返回 HTTP 200，未带密钥请求模型列表返回预期的 HTTP 401。源站的两项检查得到相同结果。通过本机默认路径和 Clash 本地代理访问管理页时，TLS 握手都失败。

Clash 的实时日志给出了原因。它在 `DIRECT` 出站时重新解析 API 域名，缓存的 IPv4 地址是 `127.0.0.1`，实际连接本机回环地址时遭拒绝。向配置中的四个直连 DNS 分别查询，发往 `114.114.114.114` 的查询返回了相同的回环地址，其余三个返回预期地址。这些结果定位了本次错误拨号，较早抓包记录的公网 TCP 重置属于另一组样本。

隔离测试使用与当前客户端相同的 Mihomo 版本。单独使用返回错误地址的解析器可复现故障。当前客户端已开启“直连域名服务器遵循策略”。测试时仅为 API 精确域名指定客户端已有的阿里 DNS over HTTPS，在相同对照配置和原有四个解析器配置下各测试两次，均通过证书验证并收到模型列表的鉴权响应。业务流量继续走 `DIRECT`。

这条 DNS 策略仍在本机设置页的草稿中时，原配置也曾恢复访问，管理页返回 HTTP 200，匿名模型列表返回 HTTP 401。该次恢复发生在保存草稿之前。

### 仅移除 114 DNS 的对照

在隔离客户端移除 `114.114.114.114`，保留其余三个直连 DNS，域名策略留空。每轮使用新的 DNS 缓存。三轮中有两轮成功访问模型接口，一轮仍拨到了 `127.0.0.1`。进一步分别查询三个 DNS 时，一次发往 `180.76.76.76` 的明文查询先收到了回环地址，再收到了预期地址。两份答复对应同一个查询标识，无法据此确定错误答复由哪台设备生成。

另一组隔离测试将直连 DNS 设为客户端已有的阿里加密 DNS，域名策略也留空。这项设置适用于所有直连域名，本次仅对 API 服务验收。三次冷启动后，实际 GET 管理页均返回 HTTP 200，匿名模型列表均返回 HTTP 401，证书校验均通过。另行发出的六次加密 DNS 查询中，五次取得预期地址，一次返回 SERVFAIL。两组对照均在隔离客户端完成。

## 规则试验已撤回

试验在隔离客户端中让公网入口走代理，私网域名优先直连。两条按公网 IP 匹配的规则还会覆盖 SSH 等其他端口。代理在测试中提供了一条可用路径，直连握手重置的触发条件仍待确认。

11 月 18 日按用户选择撤回本地试验。业务域名后缀和两台公网主机的 IP 均恢复为 `DIRECT`，文件与仓库已提交版本一致。[当前规则](../../config/clash/dmit-rules.yaml)

恢复后的文件包含 42 条唯一规则，`ruby script/clash/test-dmit-routing.rb` 的 11 组场景全部通过。历史试验参数和回执保存在被 Git 忽略的 `.private/access-regression/`。

## 11 月 19 日私网网页和 SSH 同时卡顿

用户从 Mac 的 Chrome 直接打开私网域名，登录 SSH 后也感觉回显慢。当天连续八次 `tailscale ping` 都经过同一个远端 DERP 中继，往返 326–340 毫秒。SSH 直接连接 Tailscale 地址。新建 SSH 会话至远端回显程序就绪用时 4.77 秒，在同一会话内连续八次回显的中位数为 314 毫秒，最慢一次为 673 毫秒。

| 只读对照 | Mac | 私网服务器本机 |
| --- | --- | --- |
| 三个服务入口，各新建两次 HTTPS 连接 | 首字节 1.18–1.24 秒，DNS 约 2–11 毫秒 | 通过同一 HTTPS 网关获取首字节约 19–24 毫秒，状态码分别与客户端一致 |
| 任务面板实际使用的前端脚本，各取两次 | 按域名访问 2.82–2.87 秒，固定私网地址并绑定 Tailscale 接口为 2.83–2.84 秒 | 48–53 毫秒。两端下载后解压的文件摘要一致 |
| 当时的资源余量 | — | 8 个可用逻辑 CPU，约 12.85 GiB 可用内存，采样时 CPU 空闲 99.6% |

三个服务名均解析为目标 Tailscale 地址，Mac 对该地址的系统路由属于 Tailscale。采样期间观察到了 Chrome 进程到目标私网 HTTPS 的已建立连接。表中网页时间由 Mac 发起的 HTTPS 请求测得。浏览器工具单独打开一个脚本 URL 时被客户端阻止，因此没有浏览器整页渲染耗时。

Mac 的系统网页代理关闭，Clash 生效配置中三个域名均为 `DIRECT`。在另一组对照中，手动指定本机 Clash 代理会在约五秒后失败，日志显示匹配 `DIRECT` 后拨目标私网地址超时。SSH 和绑定 Tailscale 接口的 HTTPS 在各自测试中均可连接，也都复现了高延迟。

两端的 Tailscale 检查均显示 UDP 可用、不同目的地址对应不同 NAT 映射，均未探测到可用 IPv6。服务器的 Tailscale 进程有四条已建立的 TCP 连接通向其本地出站代理，该代理也记录了对当前官方中继的代理转发。现有证据定位了中继往返带来的等待，尚不能把未建立点对点连接归因到某一端的单项设置。[Tailscale 连接类型](https://tailscale.com/docs/reference/connection-types)

### 点对点 UDP 为什么没接通

同日再次复测时，Tailscale 已换用另一个远端官方中继。Mac 与私网服务器同时向对方运行原生 `tailscale ping`，各八次均显示 DERP。Mac 当时可用的自有 Peer Relay 列表为空。

- **出站路径。** 私网服务器的 Tailscale UDP 套接字带有路由标记。对同一个 Mac 候选地址查路由，带标记时选中物理网卡，普通应用默认选中代理虚拟网卡。服务器出站防火墙放行这一标记，入站规则放行 Tailscale 的 UDP 监听。中继 TCP 使用出站代理，点对点探测另走物理网卡。
- **公网映射。** 在私网服务器上，带相同标记的单个 UDP 套接字访问两家标准 STUN 服务时，同一个出口公网 IP 出现两个不同的外部端口，回到第一个目标又得到原端口。Mac 将单个套接字绑定到物理网卡后，三个目标看到相同的外部端口，但其中一个看到另一个公网 IP。两端的 Tailscale 检测均报告目的地相关映射，没有探测到可用的 IPv6、UPnP、NAT-PMP 或 PCP 映射。
- **实际探测。** 在服务器物理网卡计数 22 秒，看到 60 个 Tailscale UDP 包发往 Mac 公布的公网候选地址，来自这些地址的反向包为零。同一采样能看到官方 STUN 请求发出和回包。观测范围限于该组候选地址，无法仅凭这段采样确定具体是哪一级 NAT 或上游过滤设备丢包。[Tailscale 设备连接与 NAT](https://tailscale.com/docs/reference/device-connectivity)

### 低延迟中继候选

从两端分别对两台现有公网候选主机的 HTTPS 监听建立三次 TCP 连接。Mac 使用物理网卡，私网服务器按 Tailscale 的路由标记发起。下表是握手耗时中位数。

| 已有候选主机 | Mac 到候选 | 私网服务器到候选 |
| --- | ---: | ---: |
| 候选 A | 12.7 毫秒 | 6.8 毫秒 |
| 候选 B | 332.6 毫秒 | 336.4 毫秒 |

候选 A 的 ICMP 探测没有回包，两端各三次 TCP 握手均成功。适合优先验证候选 A 的 UDP 可达性。本次仅测量了现有服务，Peer Relay 尚未部署，实际中继延迟需另行测量。候选角色与采样结果记录在项目的 Git 忽略私有目录中。

要实现点对点，可让一端取得公网可达的 IPv4 UDP 映射，或让两端具备可路由的 IPv6 并允许 Tailscale UDP。保留现有接入条件时，也可将候选 A 加入同一 tailnet，配置一个双方可以访问的 UDP 中继端口，并在策略中为私网服务器授予使用该中继的能力。既有服务继续按原有访问规则提供。部署后的验收应核对实际连接显示 `peer-relay` 或 `direct`，再复测 SSH 回显和相同的 HTTPS 请求。[Tailscale Peer Relay 配置与授权](https://tailscale.com/docs/features/peer-relay)
