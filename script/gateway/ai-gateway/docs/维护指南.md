# AI Gateway 维护指南

本指南说明如何维护同一个项目。执行状态见[总计划](智能网关与Guard分阶段实施总计划.md)，已完成变更见[CHANGELOG](CHANGELOG.md)。两者不互相复制完整内容。

## 代码职责与修改入口

所有 Go 代码使用一个 module `local/ai-gateway`，测试用 `go test ./...` 统一发现。Auto、Guard、模型客户端保持分包，通过 HTTP 契约联调；物理目录合并不改变输入保护的执行顺序。

| 变化 | 主要位置 | 必须同时检查 |
| --- | --- | --- |
| 增删模型、模型支持的 effort/能力 | `auto/models.go`、`auto/reasoning.go`、`auto/provider_adapter.go` | 真实端点支持、协议限制、路由/计数/缓存与 effort 矩阵 |
| 分类规则、提示词、主分类/复核 | `auto/semantic_classifier.go`、`auto/semantic_cache.go`、`cmd/auto-server` | 三语一致性、失败关闭、独立保留样本、分类用量 |
| 原生附件/Files/图片API | `auto/native_media.go`、`native_files.go`、`media_http.go`、`native_messages_bridge.go` | 三协议内容正确性、原字节、Key/区域隔离、限额/过期、Guard范围、取消/usage、真实客户端 |
| 协议输入、工具和历史续接 | `auto/protocol.go`、`auto/provider_payload.go`、`auto/history_transport.go`、`auto/tool_rounds.go` | 三协议、工具回合绑定、客户端参数清除、完整上下文 |
| SSE/上游响应协议变化 | `auto/upstream_*.go`、`auto/buffered_sse*.go`、`auto/stream_observation.go` | 完整结束、取消、畸形帧、工具/签名、大整数、失败 usage |
| 原生客户端名称、会话及agent字段 | `auto/client_compatibility.go`、`auto/client_session.go`、`auto/token_count.go` | 主/子 agent 隔离、计数来源、真实客户端压缩/取消 |
| 缓存、路由、审计和每日用量 | `auto/cache_*.go`、`auto/response_cache.go`、`auto/route_state.go`、`auto/usage*.go` | Key/区域隔离、命中仍鉴权、失败用量、重启与持久化 |
| 身份与入口配置 | `auto/pilot_auth.go`、`auto/sub2api_identity.go`、`auto/http.go`、`cmd/auto-server` | pilot仅单Key；acceptance透传各人Key复用Sub2API，HMAC标识不是数据库ID |
| Guard 输入类型、规则与脱敏 | `guard/types.go`、`guard/rules.go`、`guard/redaction.go`、`guard/preflight.go` | 脱敏完整正文、缓存前硬规则、误拦/漏扫正反对照、失败关闭 |
| Qwen3Guard/vLLM 更新 | `guard/model/client.go`、`guard/model/token_chunks.go`、`cmd/preflight-api`、`deploy/guard` | 标签解析、长输入全部分块、队列/超时、显存和并发 |
| Auto ↔ Guard 接口变更 | `auto/preflight_http.go`、`guard/types.go`、`cmd/preflight-api` | 两端同步、摘要绑定、旧接口拒绝、先 Guard 后 Auto |
| 部署、验收与构建 | `deploy/`、`tools/`、根目录两个 verify 脚本 | 新源码清单、构建上下文、端口、回退、与本地一致 |

`auto/classifier.go` 中的词表分类仍供 preview 和已有回归使用，不能误当成实际服务的语义分类器；没有从代码中删除仍被使用的路径。`auto/websocket_http.go`实现下游WebSocket到既有SSE链路的桥接；原生Codex两地101连接、增量/工具回合续接与v2压缩已有实测，旧compact适配从v10引入，具体部署和待验收项以总计划为准。

复验客户端时从已记录的修复前版本生成独立副本，排除签名/发布材料，保留原生读写/构建工具；产物复核发现的问题交回同一客户端修正。分别记录初始失败、实际改动、构建、行为适配检查和设备验证，不用退出码0或构建成功代替全部验收。仓库只保留来源、版本、结果与SHA，原始客户端日志和真实工具正文留受限位置；冻结部署源码清单不随文档补充重写。

## 版本和缓存失效

CHANGELOG 的版本是发布追踪；下面这些版本控制具体接口或缓存，不能用一个随意的 rN 替代全部含义。

| 版本 | 所在位置 | 何时更新 |
| --- | --- | --- |
| 分类策略 | `SemanticPolicyVersion`，`auto/semantic_classifier.go` | 分类 schema、提示词、难度解释或选型策略语义变化；分类缓存还包含主/复核模型名 |
| 安全规则 | `DefaultPreflightConfig().RuleVersion`，`guard/types.go` | 硬规则、脱敏或安全判定变化，使旧安全决策缓存失效 |
| 脱敏正文契约 | `RedactionVersion`，`guard/redaction.go`；Auto 在 `preflight_http.go` 校验 | wire schema 或契约语义不兼容时两端配套更新；纯规则修复不必改变接口版本 |
| Guard 模型 | `GUARD_MODEL_VERSION` | 权重、模型配置或判定行为版本变化；不能只改显示名 |
| 业务缓存模型/适配修订 | `AUTO_GATEWAY_MODEL_REVISION` | 模型目录、effort 映射、协议适配或输出语义变化；分类变化也应评估业务缓存是否仍有效 |
| 发布制品 | 源码 SHA、镜像 digest、发布标签（建立后） | 每次部署冻结，记录两地 Sub2API 版本/分组映射及配套 Guard 版本 |

纯目录重排且行为不变可保留策略/接口版本，使用新源码清单识别制品。供应商自己的 Prompt Cache 无法由网关强制清除或迁移；切模型或请求前缀变化后的收益必须实测。降级/回退若涉及不兼容缓存或会话格式，使用隔离命名空间和匹配版本的状态快照，不让旧程序直接读取未知格式。

## 上游升级流程

1. 在 CHANGELOG 的 Unreleased 写清触发原因、受影响区域/模型/客户端、旧版本和目标版本；未知项标待核验，不猜版本。
2. 对照官方文档/发布说明及实际部署版本源码。OpenAI、DeepSeek 查各自官方资料；Sub2API 查准确 tag/commit 和东京、美西运行配置，特别核对模型别名与 effort 重写。名称相同不保证行为相同。
3. 先补能复现不兼容的固定用例，再修改上述对应入口；评估是否更新分类、安全、契约和缓存版本。不要批量清除其他用户的缓存或改共享分组来让测试通过。
4. 使用不可变制品中的Python工具时加`-B`，禁止运行时字节码污染制品清单；不得把未列清单文件加入校验例外。运行根目录 `verify.sh`，保存摘要与源码清单。源文件、`auto/testdata`、`tools`、部署模板和 `go.mod` 都须打包；不能只复制 Go 文件。
5. 在独立环境用对应区域授权测试 Key 验证真实 Guard → Auto → Sub2API；单独记录直连对照、mock、本地、Linux、客户端和真实业务结果。核对 request_id、实际模型、发送/回报 effort、分类/业务 usage、错误与异常审计。
6. 达到总计划要求后再变更入口；部署前保存旧镜像/配置/状态和回退方式。配套 Guard 契约先就绪，再切 Auto。东京、美西分别验证，不能用一地结果替代另一地。
7. 将已验收内容移入 CHANGELOG 的日期/版本条目，写明实际部署位置、验证范围、已知限制与证据；未完成项留在 Unreleased。同步 README 的当前用法与总计划的待办。

## 最低回归矩阵

| 变更类别 | 必须覆盖 |
| --- | --- |
| 模型/effort/分类 | 中、英、混合；简单到复杂；逐次/跨档升级；主分类失败及复核失败；每个候选的实际参数与回报 |
| 传输/客户端/Sub2API | Chat、Responses、Messages 的同步与 SSE；工具结果、多工具、签名；计数；取消/截断；真实客户端压缩及子 agent |
| Guard/脱敏 | 正常开发、凭据解释/使用、嵌套 JSON/工具/metadata、随机签名反例；全部外发路径无合成明文残留；模型/队列/审计故障失败关闭 |
| 身份/缓存/用量 | 不同 Key 和区域隔离；撤销、过期、额度不足时连缓存也拒绝；命中/失效/重启；失败仍记录已知 token；分类和业务分账 |
| vLLM/权重/部署 | `/readyz`、真实契约、长输入不截断、目标并发与稳定性、至少10%显存余量；日志与回退演练 |

安全、协议和身份改动不能只看 HTTP 200。模型质量要检查实际开发产物；选型日志或固定题集一致率不证明模型最合适。

## CHANGELOG 与 evidence 怎么维护

CHANGELOG 是唯一变更账本，写“为什么改、改变了什么、兼容/缓存影响、验证、部署/回退、仍欠什么”。同一迭代合并条目，并列明实际改动文件或目录、对应验证和未完成项，不能只留“已整理”概述。用户追加需求后的新改动及时补记到顶部带时间/状态的条目，不倒填原完成时刻，也不把每条命令重复贴入 README。无已发布标签时使用 Unreleased 和日期，不编造发布版本。

推荐条目内容：

```text
日期 / 版本 / 状态（仅本地、隔离验收、已部署）
- 原因与变更：
- 兼容和缓存影响：
- 验证及证据：
- 部署范围和回退：
- 已知限制 / 未完成项：
```

[evidence 索引](evidence/README.md)管理证据用途和保留规则。保留真实数据、冻结题集、源码哈希、重要失败及对应修复结果；旧证据里的版本、测试数和服务器路径是历史快照。常规重复成功输出以后留一份最终结果与摘要，不再为每次试跑堆完整日志。证据进入仓库前检查脱敏，原始生产请求/Key/回答不得归档。


## 后续修改、发布和回滚方案

2026-09-16补充：以下是统一维护方案，**版本化构建、校验、install/upgrade/status/rollback已实现，并已用于4004/4005多轮版本化升级**；失败激活回退、长SSE排空、仅Auto替换及零组件重建均已有真实演练；发布工具故障矩阵已按真实/离线范围完成，具体证据和版本以总计划为准。`prepare.py`/`deploy.sh`仅负责首次创建实例，日常升级使用`tools/release.py`和`tools/deploy-release.py`。

### 一个源码项目，一份可追溯制品

所有业务修改在本仓库`script/gateway/ai-gateway`完成，同轮更新测试、兼容矩阵、总计划和CHANGELOG。服务器不直接编辑Go源码；必要的紧急修复也先同步本地后重新验证、发布。代码按需提交Git，发布标签使用`ai-gateway/v0.x.y`；只有实际获准并执行的提交/标签才记为发布，不能给尚未提交的工作区虚构commit。

运行制品是Linux amd64的`auto-server`与`preflight-api`，配套部署模板、发布说明、`release.json`与`SHA256SUMS`。源码与测试证据单独归档。编译采用固定Go工具链，通过`go build`产生可执行文件；这属于标准[Go构建流程](https://go.dev/doc/tutorial/compile-install)，无需把本项目发布成公共Go库，也无需每次在业务服务器拉最新代码编译。

release.json必须记录：发布ID/版本、Git commit或明确的dirty状态、源码清单哈希、两个二进制哈希、构建平台与Go版本、配置schema版本、Guard正文契约、安全规则/模型版本、分类策略、模型目录/业务缓存修订、状态schema、兼容的上一版、对应回归证据。正式推广拒绝dirty来源；4004未提交的开发候选可用时间+源码SHA标识，并明确标注。

同一份已验证的制品从4004推广到4000/4001，不按区域重新编译。东京/美西差异仅在部署配置和独立运行数据：上游9881/9880、端口、区域名、日志/会话状态及长期保存的内部密钥。Auto和Guard仍部署在GPU入口侧，不因此把网关代码安装到东京/美西Sub2API服务器。供应商Sub2API版本升级单独做兼容核验。

### 将版本文件与运行数据分开

实际服务器布局：制品统一进入releases目录，现有实例运行目录继续保留，不为目录整齐迁移密钥/状态。

| 位置 | 内容及约束 |
| --- | --- |
| `/data/ai-gateway/releases/<release_id>/` | 只读制品、清单与配套模板；安装后不原地修改 |
| `/data/ai-gateway/acceptance-<region>/deployment/` | 各入口的端口/区域/上游配置；版本化备份，不包含用户Key |
| `/data/ai-gateway/acceptance-<region>/secrets/` | 内部HMAC/cache secret等0400文件；升级不重建、不进入发布包 |
| `/data/ai-gateway/acceptance-<region>/state/` | 持久会话/工具绑定/分类缓存；v6采用本地文件锁事务，可由同机多个新版Auto共享；不混跑旧版单进程写入器、不使用NFS |
| `/data/ai-gateway/acceptance-<region>/logs/` | 追加审计及usage；升级不删除，不随代码回退截断 |
| `/data/ai-gateway/acceptance-<region>/backups/<deployment_id>/` | 上一版配置、发布指针、状态一致性快照、升级结果；仅授权运维可读 |

当前区域为`tokyo`（4004）和`us`（4005），各有`current-release.json`指向固定制品。4004最终切到4000时如需继承会话，必须停写后迁移同一HMAC密钥及匹配状态；否则明确创建新命名空间，不能静默改变用量标识或跨Key混用。日志保持实例维度，Sub2API数字Key对账另有定义。

### 固定升级顺序

1. **本地修改与验证**：按变更类别跑本文回归矩阵，执行verify，更新CHANGELOG；模型或协议变化还要区域真实请求对照。包内源码必须与通过验证的清单完全一致。
2. **构建一次并冻结**：生成带版本的两个二进制和SHA清单；核对依赖、兼容版本及实际通过的证据。先上传到全新release目录，校验平台、哈希、磁盘、服务端口、配套Guard契约；此时不修改当前运行实例。
3. **先更新4004**：备份配置与状态，停止接收该实例的新模型请求，让在途HTTP/SSE结束；超时仍有活跃请求时终止升级并保留旧服务，不能为强行升级切断流或让两个进程同时写状态。当前已具备信号处理、graceful shutdown、active请求统计及升级锁，WebSocket支持空闲连接关闭及在途回合排空。
4. **仅更新变化的组件**：Auto逻辑变化只替换Auto；Go安全规则变化替换Guard API；Qwen权重/vLLM更新是独立任务，需专门压测。Guard契约若不兼容，使用隔离的新Guard端口验证后再切Auto，失败保持fail-closed，不绕过安全检查。
5. **激活并验证**：实例配置指向固定release路径，按服务重新创建容器；不能只改软链接就假定单文件bind mount切到新二进制。Compose支持重建服务并保留挂载数据，见[官方说明](https://docs.docker.com/reference/cli/docker/compose/up/)。在线版本/健康只返回非敏感元数据；真实探测Key从私有文件读取，不打进包或共享为用户身份。
6. **通过后推广**：检查就绪、有效/无效Key、Guard allow/block/unavailable、中文/英文Chat/Responses/Messages、工具/SSE、会话隔离和用量对账。本期先验收4004，再按同一流程更新和验收4005。4000/4001正式切流由用户明确排除，另行授权后才执行；每个区域独立核验。
7. **失败回退并留证**：激活或验证失败时停止新增实例、恢复旧发布路径与配置并重新验证；写部署账本和CHANGELOG。没有新业务写入时可恢复状态快照；有新业务写入后，只允许旧程序兼容新状态再回退，不能覆盖新增工具绑定或丢弃usage。不能兼容时保持该入口不可用并按修复方案处理，不自动丢数据。

最脆弱的前提是**旧版本能读升级后的持久状态**。发布时必须明确schema兼容关系并在4004演练；声明无法回退的版本不能自动推广。仅Guard回退时，旧Auto可能仍处于drain；入口保持关闭，恢复Guard后先解除Auto drain再做就绪检查。升级失败时旧服务也不可用，需要明确报警和人工处理，不能误报自动回滚成功。

### 发布工具的验收范围

已提供`release.py build/verify`及`deploy-release.py install/upgrade/status/rollback`，版本及生命周期共用`service/lifecycle.go`。构建仅接受与验证清单完全一致的源码，vendored依赖一并校验；正式release拒绝dirty来源，当前候选明确标注candidate_only。运维status/drain需内部密钥，不向用户入口公开。

发布工具须对以下情况给出明确结果：首次安装、重复安装相同版本、源码/二进制哈希不符、错误CPU平台、配置/契约不兼容、密钥缺失、并发升级、长SSE未排空、磁盘不足、Guard不可用、激活失败、回退失败。必须实际演练升级与回退，验证用户Key仍归Sub2API、内部密钥不变、会话/日志/usage不丢、线上版本与本地制品一致。JSONL轮转与磁盘告警同时纳入生产前置项，不以容器stdout轮转代替业务日志维护。

当前没有承诺零停机。v6已支持同机多个新版Auto事务访问共享卷，但旧版写入器不具备相同锁协议；升级仍先排空并保持schema兼容。跨主机存储、负载均衡及无损状态迁移必须另行验收，不能仅增加副本数。

### 固定候选的真实项目能力比较

`cmd/model-profile` 是独立评测入口，须显式传 `--fixed-candidate-evaluation`、回环 `--listen`、`--region`、区域 `/v1` 的 `--upstream`、真实 `--guard`、候选 `--model`、固定原生 `--effort` 和不存在的 `--output` 目录。使用对应区域本人或已创建的专用测试Key，鉴权/夜间策略仍由原Sub2API决定；不改共享分组。程序不读客户端effort，不使用整段响应缓存，不在失败后换候选。

每个候选必须使用相同修复前项目副本、需求、工具权限和构建/行为检查；保留初次失败及评审修正次数，原项目不改。原始请求、模型改动和构建日志留受限目录，仓库只存来源、SHA、结果和计量摘要。`fixed-model-capability-profile-v1` 标明固定候选比较，不能把该结果写成Auto自然选型的通过率。工具已完成v14完整验证与真实SSH合成任务闭环；真实模型任务及产物比较状态以总计划P04为准。

### OpenCode 用户命令与模型工具续接

原生OpenCode会把用户直接运行的task/bash命令编码为完整工具调用与结果；此类ULID不是上游返回的call_id。候选先验证身份及Guard，再查同区域/Key/协议的已发工具绑定；已有绑定始终优先，精确匹配原生本地单对记录且无绑定时才按用户完整历史继续。UA、提示文字和ULID是兼容结构，不是授权信息，不允许读别的Key的隐藏上下文。普通工具续接缺绑定仍失败关闭。证据来自OpenCode1.18.4本机原生请求与[对应版本源码](https://github.com/anomalyco/opencode/blob/v1.18.4/packages/opencode/src/session/prompt.ts)，当前仅候选修复，未部署。

固定候选任务驱动为`tools/model_profile.py`。操作者先准备私有脱敏历史副本、明确read_globs/write_globs和固定checks；模型只能读写声明文件，不获得shell或签名材料。通过`--ssh qiyuan-gpu`可使用GPU回环评测端点，Key从GPU私有文件读取。原始请求/回复/构建日志保留在0700输出目录，仓库只存哈希与元数据。失败、轮数上限、构建通过和产物评审分别记录；构建通过不表示任务质量或真机UI通过。

取消对账使用`tools/reconcile_acceptance.py`，配置中每个scope可给`audit_glob`。只有严格关联到未完成的取消/交付失败终止审计，且已收token不超过最终账单时，才标记`confirmed_partial_usage_with_final_bill`；保留原始部分数值，不能把它称为最终token一致。缺证明的差异仍失败，未知用量仍未知。

## 模型画像工具的传输边界

`tools/model_profile.py`只在已授权的脱敏历史副本中提供限定文件工具和固定离线检查命令；每个候选从相同初始文件清单开始，固定模型不等于自然Auto路由。私有源码外发仍按具体授权范围执行，签名材料和环境凭据不在读取范围。

跨本机/GPU使用一个SSH exec会话传送多轮结构化请求，Key留在GPU，逐请求真实Guard和对应区域Sub2API不变；不创建SSH端口转发，不修改全局SSH配置。建连、响应均有时限，响应丢失或连接中断立即停止，不自动重放。原始转录仅留私有目录；仓库只保留来源、SHA、检查和结果。源码无改动时的基线构建通过，不能记为任务完成。
