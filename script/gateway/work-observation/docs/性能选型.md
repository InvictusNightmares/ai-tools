# 运行性能选型

日期：2026-09-17。状态：基础对照已完成，Go完整采集已完成一批实测，最终功能和性能验收仍未完成，未部署正式采集。

## 决策依据

采集独立于Sub2API，不要求使用Go。先满足原生协议、完整性和附件元数据要求，再比较本机真实负载；不能仅根据编程语言、框架宣传或其他公司的压测作决定。

| 方案 | 本次检查 | 处理 |
| --- | --- | --- |
| Nginx mirror | 只镜像请求；开启request body mirror会先读完整正文，并使unbuffered request proxying失效 | 不足以实现本计划的响应/双向会话采集，不作为完整方案 |
| Envoy HTTP tap | 当前官方仍标实验状态；还需补受限存储及双向会话关联 | 不直接作为完整采集方案 |
| Rust/Pingora 0.9.0 | 请求块、上游响应块及升级后的数据经过可编程钩子；可复制Bytes引用后非等待提交 | 基础实验完成；短请求/WS延迟较低，完整采集仍待验收 |
| Go ReverseProxy | 标准库转发，对正文读取和升级后的双向流做只读旁路 | 基础实验完成；长文本CPU/RSS较低，完整采集仍待验收 |

Pingora的支持结论基于固定0.9.0源码，不将main分支的新接口当成已发布接口。实验只使用现有链路所需的明文HTTP内部上游，不擅自打开实验性TLS模块。

实测120组、37,560次请求全部内容校验成功；双方仍存在超过5%的采集增量场景，未选定可部署制品。[完整基础实验结果](evidence/2026-09-17-proxy-selection/README.md)保留失败和测量边界。

Go完整采集最新dev.8完成63组/8,820次，14,364条记录无缺失，四原生客户端另行通过。但三轮合并的8MiB JSON总耗时开关增幅5.60%、64KiB WS为15.52%，仍未达5%门槛；约4KiB WS新增整个代理路径总耗时30.72%。无正式接入，不能声明Go已证明最快。dev.5长输入的截断失败、dev.6/7/8优化和每轮数据见[完整采集阶段结果](evidence/2026-09-17-collector-r1/README.md)。独立数据卷对端到端性能的影响尚未纳入，最终必须复验。

## 实验及验收分层

1. **基础转发实验**：Nginx→合成上游，对比Nginx→Go/Pingora→同一上游。候选分别关闭采集、开启有界提交及后台SHA256。小JSON、1MiB/8MiB长输入、SSE、WebSocket；相同CPU和内存限额，轮换次序，重复三轮。
2. **完整采集验收**：加入协议解析、附件元数据和受限明文存储后重新测量。队列满/磁盘满/断网/进程重启/30天清理都需验证，不能由第一层推定通过。
3. **客户端与接入验收**：四个原生客户端的工具、压缩、取消、恢复和附件，最后才按东京→美西接入顺序执行。

报告首次正文/总耗时p50和p95、吞吐、CPU、RSS、错误、采集丢失。首字节定义为首次响应正文字节，SSE为首个正文事件的到达，不用连接/响应头时间替代。额外报告8回合WebSocket会话耗时，不能与单HTTP请求混为同一计量单位。CPU统计包括预热，报告字段明确标记。

生产验收保持p95首段输出和总耗时增幅不超过5%。若基础实验出现更差结果，先定位连接复用、拷贝、线程调度和缓冲行为，不把远端模型本身较慢当成代理开销可忽略的理由。不同指标各有胜负时按正常负载分布与尾延迟选择，不声称全球最快。

## 实现约束

- 前台只做转发所需动作和有界、非等待提交；后台独立执行附件元数据提取、持久化，离线分析不进入转发路径。
- 缓冲不足降级采集、标记缺失；不得等待磁盘、延迟业务、静默截断或将正文混入普通运行日志。
- 保留真实UA及协议内容；采集不能改写上游的业务请求、模型选择或附件。
- 任何候选代理仍是新增链路进程，需要故障与回退验收；“后台故障不阻塞”不等于代理进程本身永远不会影响业务。
