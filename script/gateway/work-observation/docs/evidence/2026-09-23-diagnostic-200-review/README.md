## Guard 拦截与 Auto 403：结果复核

58 条 Guard 明确拦截的原因码互斥：`request_shape_limit` 47 条、`session_quarantined` 7 条、`secret_input_not_allowed` 4 条。不能把 58 条都算作恶意输入，也不能在人工真值为 0 时计算误拦率。

对 47 条形状限制样本，在受限目录内逐条校验源记录 SHA 后，只统计请求/回复消息和工具个数。仓库 Guard 默认阈值为消息 128、工具 32、附件 16；`guard_payload()` 当前把**模型回复也加入输入消息**：

| 47 条的触发形态 | 条数 | 对 Guard 指标的含义 |
| --- | ---: | --- |
| 请求自身超过 128 条消息 | 32 | 命中请求形状上限；是否应拦截仍需结合产品边界复核。 |
| 请求消息未超限，但请求工具超过 32 个 | 3 | 命中工具形状上限。 |
| 请求消息和工具均未超限，只因合入模型回复才超过 128 条消息 | **12** | 离线输入构造导致的形状拦截，不能作为正式输入 Guard 的有效安全标签。 |

这 12 条的诊断序号为 22、23、43、52、58、78、79、88、92、128、133、136。分析目标仍需要保留模型回复和工具过程，但**输入安全判定**与**回复/质量观察**应分开记录，避免后者改变前者的分母和结论。7 条会话隔离也依赖历史状态，不能当作 7 次独立有害内容判定；4 条凭据使用拦截需在受限页面逐条核对实际意图。

23 条 Auto HTTP 403 的响应码全是 `preflight_blocked`，不是 Auto 模型的任务拒绝：其中 17 条已有 Guard 拦截、2 条 Guard 无结论，按当前顺序本不应再执行 Auto；另 4 条 Guard 放行而 Auto 二次预检拦截（序号 96、107、131、135），需核对两个预检所见的输入契约/状态。`auto_state=blocked` 或页面“Auto 被拒绝”不能直接用作 Auto 选型标签。

54 条 Auto 返回模型中，`deepseek-flash` 52 条、`gpt-5.6-luna` 2 条；有 1 条的 Guard 已拦截，因此可进入选型复核的是 **53 条**。其中 7 条带长上下文或工具特征（序号 4、30、70、80、111、118、127），适合优先检查能力匹配。现有元数据不能判断这 53 条选型是否合理、过强或过弱，也不能证明 Astra/Sol 可以安全降到低档模型。

## 优先复核与修改清单

1. **先修指标口径和离线输入**：Guard 输入判定只用实际请求；回复、工具结果及后续纠正另作观察，保留关联但不回灌输入拦截。把上述 12 条从输入 Guard 标签候选中剔除。给 69 条 Guard 非放行却有 Auto 状态的历史样本加显式旧版/不可评估标记；同版本比较时只用 86 条放行子集。
2. **拆开 403**：将 Auto 的 `preflight_blocked` 与身份鉴权 403、模型选择分别呈现；优先核对 Guard 放行而 Auto 二次预检拦截的 4 条。人工复核队列同时保留凭据拦截 4 条（5、6、7、17）和会话隔离 7 条（1、25、36、53、55、61、71），但不预填对错标签。
3. **恢复技术可解释性**：为身份检查 503 添加无正文的阶段子码（配置、网络超时、上游 HTTP、响应格式），不跳过 Sub2API 授权；为分类器 503 记录请求形状/截断与主分类、复核失败阶段。用固定、已授权的少量样本对 21/4/4 条 Guard 放行失败分别复现，先消除技术失败再评价路由。
4. **冻结人工真值后再比较策略**：在复核页逐条标注 Guard 与 Auto，记录“无法判断/技术失败”；按任务而非同一请求的多次尝试划分验证集。用相同 200 条比较基线与候选 4004/4005 的技术可用性和质量，再决定是否扩大至 200–500 条人工确认任务。没有完成这一步前不训练候选模型、不讨论替换正式 4000/4001。
