# 正式入口工作过程采集

目标是让Guard与Auto能够结合完整工作过程分析用户请求与模型回复，定位误拦、错误选型、返工和质量问题。独立维护4000/4001的持续采集、受限存储和滚动分析；不参与业务鉴权、选型或Guard决策，不改变客户端使用方式。2026-09-20 已将 candidate-r3 采集旁路正式接入 GPU 的 4000/4001，长期 watchdog 负责采集故障时自动回退。

## 先区分两类“日志”

现有4000/4001的访问、用量和`policy-log`记录不是全量工作过程：它们可以提供请求量、模型、Token、费用、耗时以及部分异常/拒绝证据，但通常没有正常请求正文、完整模型回复、流事件和工具回合。因此，**“现有日志只能做流量和模型分布统计”描述的是接入本采集器之前的旧记录，不是本项目的目标或能力上限。**

`work-observation`本身就是要补上的独立采集代理。它以GPU上的反向代理方式接收原本进入4000/4001的流量，复制网关可见的完整请求、可见回复、有序HTTP/SSE/WebSocket事件、工具调用/结果、错误、取消和缺失信息；之后由`tools/evidence.py`生成受限正文证据，再由`tools/semantic.py`在离线平面调用Guard和Auto预览。`tools/analyze.py`只负责不含正文的滚动统计，不能代表整个采集器只做统计。

这里的“全量”是**经过采集代理且网关可见的事件**，不是无条件抓取一切：鉴权头不落盘，附件二进制只留元数据，客户端未发送的本地文件和模型未返回的内部思考不可见；队列、容量、解析或存储失败必须写入缺失账本。采集器仍只允许在 Nginx 共享网络命名空间内回环监听；正式入口已经通过内部 `proxy_pass` 接入，宿主公网不暴露采集端口。

## 已批准边界

- 持续采集直到手动关闭；每条原始文本正文保留30天。
- 用户明确取消正文脱敏：普通文本、工具参数/返回文本按原文完整记录，不做敏感词、凭据模式或字段替换；附件仅元数据，不复制二进制。
- 按用户后续确认，独立代理部署在GPU，Sub2API源码、镜像及升级流程不变；GPU受限明文保存，不做落盘加密，上限200GiB。两地临时缓冲和跨服务器正文传输不再需要。
- 保持4000/4001现有鉴权和选型，不执行正式Auto/Guard切流；采集代理通过隔离验收后才接入内部转发。4004/4005继续用于Guard/Auto候选验证。
- 每5分钟完整性检查、每小时增量分析、每天趋势报告；生产实际与离线模拟分开。
- 外部模型不得自动收到员工正文；正常业务优先于采集，缺失显式记录。

## 分析对象与边界

[内容契约](docs/采集与分析内容契约.md)定义完整请求/回复、内容来源、会话关联、缺失和离线结果。不能以元数据统计替代Guard/Auto语义分析；不能用最后一句问题替代完整上下文。附件语义、未被客户端发到网关的本地文件、未公开的模型内部思考均不在首期可见范围。

## 目录职责

`source/`保存采集模块，`cmd/`保存服务和管理命令，`tools/`保存构建、查询及分析工具，`deploy/`保存配置和定时任务模板，`tests/`保存工具回归，`docs/`保存验收证据和运维说明。语言不预先限定；`experiments/`保存选型实验，不能作为部署制品。

用户要求优先运行性能。当前采集制品选用Go：前台只做有界、非等待的采集提交，附件元数据提取、持久化和统计由后台完成；独立分析程序不进入转发路径。Go与Rust/Pingora的对照及完整采集基准均保留，性能门槛仍以同一GPU三轮实测为准。

[性能选型依据](docs/性能选型.md)与[独立实验](experiments/README.md)保存验证边界。`tools/analyze.py`已提供本地采集导出的幂等导入、滚动统计和30天索引清理；`tools/health.py`检查丢失、积压、磁盘、陈旧状态及重启后的计数。两者不保存正文、不联网；另有`tools/evidence.py`保留完整内容证据，三者已通过独立合成回归（最新结果见CHANGELOG）。已接通合成实验采集；尚无正式用户工作分析结果，滚动调度代码和systemd模板已完成隔离测试，尚未启用正式调度。

Sub2API基线为0.2.4+policy-log.8，仅用于账单对照，不重新编译或部署。原`../policy-log/`继续负责政策拒绝证据。独立代理先在隔离端口验证，通过后调整GPU原Nginx的内部转发，客户端地址保持4000/4001。关闭正文采集不改变转发；完整回退恢复原Nginx上游。代理进程本身退出仍属于新增链路故障，不能把存储失败不影响转发夸大为整个代理零风险。

## 开发进展

`observation-dev.9`在dev.8基础上增加不含正文的持久缺失账本；已有四原生客户端33项流程、69条HTTP交换通过，含工具、压缩、子任务、取消恢复和图片；原生Codex WebSocket另6项通过，31条记录无缺口。图片原样到达上游，采集仅留元数据；原生测试使用合成服务，不代表模型任务质量或Windows历史故障已解决。dev.9已在GPU隔离目录完成gofmt、race、vet和`CGO_ENABLED=0` Linux构建，详见[Go验证证据](docs/evidence/2026-09-17-collector-r1/dev9-go-validation.json)。

2026-09-20已完成真实GPU拓扑的只读审计，并在不改4000/4001业务代码的前提下验证共享Nginx网络命名空间sidecar：东京`127.0.0.1:18400`、美西`127.0.0.1:18401`均能访问原upstream并返回200。candidate-r3 使用统一200GiB卷正式接入：4000→18400、4001→18401；两端容器内外配置SHA一致，正式请求均返回200，capture已打开。由于生产 Nginx 对单文件配置使用只读 bind mount，切换脚本在配置原子发布后重启对应容器使新 inode 生效，并保存可验证回退副本。

随后统一200GiB卷已挂载并承接candidate store；Tokyo与US各完成一次60秒受控短窗口，watchdog采样12次、Nginx新增5xx为0并自动回退。两次窗口只有采集器自检根路径事件，未产生真实员工工作样本，因此仍不能签收真实p95或Guard/Auto质量结论。

在正式接入前又完成两地600秒观察窗口，watchdog各采样118次，5xx、丢失和回退错误均为0。正式接入后的长期 watchdog 当前以 `--seconds 0 --interval 5 --max-5xx -1` 无期限运行；最近复核 Tokyo/US 的采集器均为 `capture_enabled=true`，错误和丢失计数为0，4000/4001 返回200且采集计数持续增长。该接入只负责保存工作过程，不代表 Guard/Auto 已经消费或训练这些数据。

滚动分析现在包含独立的`tools/semantic.py`本地复核worker：它从已校验的完整事件读取请求和回复，在`plane=offline_analysis`下分别调用配置的公司内网Guard预检与Auto`/v1/route`预览，只保存决策、原因、分类和模型结果，不把正文复制到SQLite，也不执行生产工具。默认配置仍关闭；端点只允许回环或私网地址，Guard/Auto任一不可用会保留队列并标记待复核，进程中断后的running任务会重新排队。使用专用认证文件调用 Auto 时，同时转发事件记录的真实`User-Agent`，不会从采集正文重建鉴权头。8095/8096的候选 Auto 仅在 route-preview 模式读取两地0600 semantic Key 文件，生产 regional 服务仍禁止共享分类器 token、继续透传调用方凭据；远端可用性需用审计日志复核。合成回归已覆盖放行、block终态、不可用、陈旧任务恢复、正文不落分析库、公共端点拒绝和认证文件边界，54项Python测试通过。它证明了本地分析链路可用，尚不等于真实员工样本已经分析。

最新完整压测63组/8,820次响应一致，14,364条记录零采集缺失；优化已降低大消息平均采集开销，但单轮p95仍有波动，最终5%门槛尚未签收。当前正式接入由无期限 watchdog、路径探针和自动回退保护，真实样本的p95仍需继续观察，不能把接入本身当作性能验收通过。滚动统计改为SQL聚合，100万条合成记录已验证；不等于Guard/Auto语义分析完成。完整状态、失败及待办见[阶段证据](docs/evidence/2026-09-17-collector-r1/README.md)和[运行与验收](docs/运行与验收.md)。
正式数据覆盖、报告边界和后续缺口见[滚动分析状态](docs/滚动分析状态.md)。
